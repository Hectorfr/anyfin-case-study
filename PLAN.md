# Track A transaction classifier development plan

Build on the current high-confidence rules in `predict.py`. The goal is to raise the case score, which gives +1 for a correct label, −1 for a wrong label, and 0 for `unknown`. Keep `data/train.csv` (558 labelled rows) for building and tuning, `data/dev.csv` (138 labelled rows) for comparing runs, and the official `data/validation.csv` (1,183 unlabelled rows) as the final local test input. The organizers' hidden set is a separate final evaluation.

## Ground rules for comparisons

- Freeze the train/dev split generated by `make_split.py`. Fit merchant mappings and models only on `data/train.csv`; never use `data/dev.csv` labels to populate a lookup table. The official unlabelled test rows were inspected during baseline setup; from now on, do not use them to build aliases or rules.
- Keep the one-command interface: `python predict.py INPUT.csv` writes `id,category`. Predictions must come from the code, with no row-ID-specific answers.
- For each candidate, record dev score, correct/wrong/unknown counts, precision, coverage, errors by category and bank, runtime, and estimated API cost. Save the exact command and configuration so runs can be compared.
- Baseline on the fixed dev split: **35 correct, 0 wrong, 103 unknown; score 25.36 per 100**. The rules were written after inspecting the full original ledger, so this is a comparison baseline, not a blind estimate of future accuracy.

## 1. Merchant matching

- [x] Extract the underlying merchant from bank prefixes, card dates, reference numbers, and payment-provider wrappers. Preserve the original text and distinguish a provider invoice (such as `KLARNA AB`) from a purchase routed through that provider (such as `KLARNA*SHOP`).
- [x] Build a merchant-to-category index from **train only**. Use exact normalized matches first. If a merchant has conflicting labels, abstain until the context resolves them.
- [x] Add conservative fuzzy matching for spelling variants and abbreviations. Require both a strong similarity score and a clear lead over the second candidate; genuinely new businesses go to the fallback.
- [x] Inspect errors on train-only held-out description groups while developing the matcher. Compare the frozen rules-only, exact-match, and fuzzy-match variants on dev.

**Exit check:** A higher dev score than 25.36, reproducible predictions, and no evidence that bank wrappers or payment providers are being mistaken for the merchant.

Result: **29.71** on the fixed dev split (41 correct, 0 wrong, 97 unknown). See [RESULTS.md](RESULTS.md). Fuzzy matching has synthetic typo coverage but no additional dev matches yet.

## 2. Model or LLM fallback

Local text experiment: an optional character n-gram logistic model selected a 0.60 threshold on train-only grouped folds. It scored **34.06** on dev (48 correct, 1 wrong, 89 unknown) versus 29.71 without the model. It is not the default because six of seven added correct rows repeat one business and its score is uncalibrated. See [RESULTS.md](RESULTS.md).

The batched Claude Haiku 5.5 fallback raised the dev score to **91.30** (127 correct, 1 wrong, 10 unknown) with the final response limit. Its high-certainty and evidence gate is empirically precise on this small split but not probability-calibrated. See [RESULTS.md](RESULTS.md).

- [x] Apply the fallback only where rules, merchant matching and the local text model return `unknown`. Compare the local text model with Claude on the same dev rows using text, direction and account context.
- [x] Make the output one valid taxonomy label or `unknown`. Use a fixed prompt, structured response, repeated-description cache, batches, and a key from an environment variable or ignored `.env` file.
- [ ] Measure incremental score, latency, and cost over the merchant matcher. Check the case limits of under 10 minutes and $5 for 5,517 hidden rows, and estimate what 10 million rows per month would cost. Keep the local model if an LLM cannot meet those limits.

**Exit check:** The fallback improves total dev score after its mistakes are counted, and the end-to-end run fits the case's runtime and cost limits.

## 3. Abstention and final selection

- [ ] Assign a confidence estimate to each prediction source. Calibrate it with train-only held-out groups where possible; an LLM's self-reported confidence is not automatically a probability.
- [ ] Return `unknown` when the estimated chance of being correct is too low or sources conflict. With +1/−1/0 scoring, the theoretical cutoff is **above 50%**; use a safety margin if calibration is weak or the merchant/bank is unfamiliar.
- [ ] Calibrate candidate thresholds on train-only held-out groups. Compare a small, fixed set on dev, then lock the chosen configuration rather than repeatedly tuning to the 138 dev rows.
- [ ] Run the locked code on `data/validation.csv` as the final local test. Verify 1,183 unique IDs, valid categories, runtime, and cost. Do not infer accuracy from this unlabelled file. Keep the five-line submission README and the command up to date.

**Exit check:** Select the configuration with the best credible dev score and acceptable cost, then generate the official predictions from that frozen code.

The candidate [solutions.csv](solutions.csv) was regenerated with `--full-training --text-model --claude` after the split-trained version scored 91.30 on dev. Its 1,183 IDs and categories were validated, but its accuracy cannot be measured without validation labels.
